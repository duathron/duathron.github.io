A machine has been compromised. The only evidence: a packet capture recorded during the attack. The task splits into two phases — first, reconstruct what the attacker did by analysing the PCAP in Wireshark. Then, use the same attack path to hack back in and retrieve the flag.

This is the first room I've done that combines both blue and red team work. Part 1 is pure forensics — reading traffic, understanding the attack chain. Part 2 flips the perspective: replicate the attack yourself against a live target.

---

## Theory

### FTP and Why It Matters in Forensics

FTP (File Transfer Protocol) transmits everything in cleartext — credentials, commands, file contents. This makes it a forensic goldmine in packet captures: every login attempt, every uploaded file, every directory change is readable in plain ASCII. The same property that makes FTP useful for forensic analysis is what makes it dangerous in production — anyone capturing the traffic sees everything. This is the same principle as the NFS traffic in [[2026-02-19-hfb1stolenmount]], where unencrypted protocol traffic revealed the entire exfiltration chain.

### Brute Force Attacks

A brute force attack systematically tries credentials from a wordlist against a login service until one succeeds. In the PCAP, this is visible as a rapid sequence of failed login attempts followed by a single success. Tools like Hydra automate this process across multiple protocols — FTP, SSH, HTTP, and others.

### PHP Reverse Shells

A reverse shell is a connection initiated by the target machine back to the attacker, bypassing firewall rules that would block incoming connections. PHP reverse shells are commonly used when an attacker can upload a `.php` file to a web server — accessing the file via HTTP triggers the script, which connects back to the attacker's listener. The same delivery mechanism appeared in [[2026-02-23-infinity-shell]], where a PHP webshell (`images.php`) was planted in a CMS image directory. The difference: that was a one-liner executing URL parameters, while this room uses a full reverse shell that establishes a persistent connection.

## Part 1 — Traffic Analysis

### Opening the PCAP

The room provides `Capture_1612220005488.pcapng` for download. Opening it in Wireshark, the traffic is predominantly FTP — dozens of login attempts from `192.168.0.147` to `192.168.0.115`, followed by TCP and HTTP traffic later in the capture.

### Identifying the Brute Force Attack

Filtering for FTP PASS commands (`_ws.col.info contains "PASS"`) reveals the attack immediately: a rapid sequence of password attempts using common credentials — `111111`, `123123`, `1234567`, `654321`, `sunshine`, `abc123`, `qwerty`, `football`, and many more. This is a dictionary attack using a well-known wordlist pattern.

<img src="/assets/img/posts/h4cked/pass-filter.png" alt="Wireshark display filter showing FTP PASS requests — a rapid sequence of common passwords being tried against the server" width="700">

The targeted username is visible via **Tools → Credentials**: every single login attempt uses the account `jenny`.

<img src="/assets/img/posts/h4cked/credentials.png" alt="Wireshark Credentials dialog showing all FTP login attempts using username jenny" width="700">

### The Successful Login

Scrolling to the end of the PASS sequence, frame 394 sends `PASS password123`, and frame 395 returns `230 Login successful`. Out of all the passwords tried, `password123` was the one that worked.

<img src="/assets/img/posts/h4cked/login-success.png" alt="Frames 394 and 395 — PASS password123 followed by 230 Login successful" width="700">

### Reconstructing the Attack Chain

Filtering for `ftp` (command channel only) reveals the complete post-authentication activity in chronological order:

<img src="/assets/img/posts/h4cked/ftp-overview.png" alt="Full FTP command sequence after login — PWD, LIST, TYPE I, PORT, STOR shell.php, CHMOD 777, QUIT" width="700">

The attacker's actions after login:

1. **`PWD`** — checks the current directory. The server responds: `/var/www/html` — the default Apache web root. This means any file uploaded here is directly accessible via HTTP.

<img src="/assets/img/posts/h4cked/pwd-response.png" alt="FTP PWD command showing /var/www/html as current directory" width="700">

2. **`LIST -la`** — lists the directory contents to see what's on the server.

3. **`TYPE I`** — switches to binary transfer mode for the file upload.

4. **`STOR shell.php`** — uploads a file called `shell.php` to the web root. The corresponding FTP-DATA packet (frame 431) shows the transfer: 5493 bytes.

<img src="/assets/img/posts/h4cked/stor-command.png" alt="FTP STOR shell.php command — the attacker uploading a reverse shell to the web root" width="700">

<img src="/assets/img/posts/h4cked/stor-data.png" alt="FTP-DATA frame showing 5493 bytes transferred for shell.php" width="700">

5. **`SITE CHMOD 777 shell.php`** — makes the file world-executable. Without this, the web server might not execute the PHP script.

6. **`QUIT`** — closes the FTP session.

### Post-Exploitation — The HTTP Stream

After the FTP session ends, the traffic shifts to HTTP and TCP. The attacker accesses `http://192.168.0.115/shell.php` in a browser, which triggers the reverse shell. Following the HTTP stream (right-click → Follow → TCP Stream on the relevant packets) reveals the full post-exploitation session:

<img src="/assets/img/posts/h4cked/http-stream.png" alt="HTTP stream showing the reverse shell session — whoami returns www-data, followed by ls -la of the root filesystem" width="700">

The stream shows:

- The shell connects back as `www-data` (the Apache service account)
- First command: `whoami` — confirms execution context
- The attacker spawns a proper TTY shell, switches to user `jenny` (password reuse — the same `password123` from FTP works for the system account), then escalates to root via `sudo su`
- As root, the attacker clones the **Reptile** rootkit from GitHub — a kernel-level rootkit designed to hide processes, files, and network connections from detection

The transition from FTP upload to HTTP execution to reverse shell is also visible in the raw packet list — the protocol shifts from FTP to TCP/HTTP right around frame 447:

<img src="/assets/img/posts/h4cked/ftp-to-http.png" alt="Packet list showing the transition — after STOR shell.php and CHMOD 777, the attacker accesses shell.php via HTTP, establishing the reverse shell" width="700">

## Part 2 — Hack Back

### Objective

The machine has been compromised, the attacker changed configurations, but the vulnerability is still there. The task: use the same attack vector to regain access and read the flag from `/root/Reptile/flag.txt`.

### Brute Force with Hydra

Since the PCAP revealed that `jenny`'s FTP credentials were brute-forced from a wordlist, the same approach works against the live target. The attacker changed the password, but it's still a weak one:

```bash
hydra -l jenny -P /usr/share/wordlists/rockyou.txt ftp://TARGET_IP
```

<img src="/assets/img/posts/h4cked/hydra.png" alt="Hydra brute force result — login jenny, password 987654321 found" width="700">

Hydra finds the new password quickly. It's another entry from the `rockyou.txt` wordlist — the password was changed, but not to anything stronger.

### FTP Login and Shell Upload

With the credentials, the next step mirrors the attacker's approach: log in via FTP, upload a PHP reverse shell, and set permissions.

Before connecting, the reverse shell script needs to be prepared — a PHP reverse shell (like the one from [pentestmonkey](http://pentestmonkey.net/tools/php-reverse-shell)) with the attacker IP changed to your own TryHackMe VPN IP and the listener port set to your chosen value.

```bash
ftp TARGET_IP
# Login as jenny with the recovered password
put rev-shell.php
chmod 777 rev-shell.php
```

<img src="/assets/img/posts/h4cked/ftp-upload.png" alt="FTP session — logging in as jenny, uploading rev-shell.php, setting chmod 777" width="700">

### Catching the Reverse Shell

In a second terminal, start a Netcat listener on the port configured in the reverse shell script:

```bash
nc -nlvp 5555
```

Then trigger the shell by navigating to `http://TARGET_IP/rev-shell.php` in the browser. The listener catches the incoming connection:

<img src="/assets/img/posts/h4cked/reverse-shell.png" alt="Browser triggering rev-shell.php, Netcat listener catching the reverse shell — whoami returns www-data, su jenny with recovered password, escalation to root" width="700">

From there, the same privilege escalation path works: `www-data` → `su jenny` (with the brute-forced password) → `sudo su` to root. Navigate to `/root/Reptile/` and read the flag.

## Lessons Learned

**Unencrypted protocols tell the whole story.** FTP's cleartext nature made the entire attack reconstructable — every password attempt, every command, every uploaded file. This is the same lesson as [[2026-02-19-hfb1stolenmount]] with NFS: unencrypted protocols are forensic goldmines for defenders and massive risks in production.

**The PCAP is the playbook.** Part 2 didn't require any creativity — the attacker's exact methodology was documented in the traffic capture. The same credentials approach, the same upload path, the same privilege escalation chain. In a real incident, a thorough PCAP analysis doesn't just explain what happened — it reveals what's still exploitable.

**Password changes mean nothing without stronger passwords.** The attacker changed jenny's password after compromise, but picked another `rockyou.txt` entry. Hydra cracked it in seconds. Changing a weak password to another weak password is not remediation.

**Perspective switching builds understanding.** Analysing the attack from the blue team side first, then replicating it from the red team side, made the entire chain click in a way that pure analysis wouldn't. Seeing the `STOR shell.php` in Wireshark is one thing — actually uploading the shell and catching the callback yourself connects the theory to practice.

**Follow → TCP Stream is the single most useful Wireshark feature for understanding post-exploitation.** The FTP command channel shows the file operations, but the HTTP stream shows what happened after the shell connected — the full terminal session, including privilege escalation and rootkit installation. Without following that stream, the attack would have looked like it stopped at the file upload.
